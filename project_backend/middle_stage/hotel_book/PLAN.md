# AI 酒店预订平台实施计划

> 文档状态：v1.0  
> 项目目录：`D:\qwen_compitition\hotel_book`  
> 关联客户端：`D:\qwen_compitition\Qwen_competion` 中的 React / Tauri Android 客户端

## 1. 项目定位

建设一个同时服务于酒店、普通用户和 AI Agent 的酒店预订平台：

- 酒店可以维护酒店资料、地理位置、房型、每日价格、可售日期、库存数量和退改规则。
- 用户可以通过 Web 或现有手机 App 搜索酒店、查看详情、提交订单、支付、取消和查看订单。
- AI 可以通过稳定、结构化、可审计的 API 完成“搜索—报价—确认—占房—支付—查单/取消”流程。
- 所有前端和 AI 使用同一个后端作为价格、库存、订单和状态的唯一可信来源。

这个项目不是单纯的酒店展示页。第一优先级是保证库存不超卖、报价可追溯、订单可恢复，以及 AI 不会在没有用户确认时误下单。

## 2. 产品目标与成功标准

### 2.1 MVP 目标

1. 酒店可以注册并维护一家或多家酒店。
2. 酒店可以创建房型、价格计划，并按日历批量维护价格和库存。
3. 用户可以按目的地、日期、人数、房间数和价格范围搜索。
4. 用户可以完成一次真实、可追踪的预订流程。
5. AI 可以只依赖公开 API 完成相同流程，不需要操作网页或解析自然语言页面。
6. 现有手机 App 可以增加“酒店”入口并复用这套 API。
7. 多个用户或 AI 同时预订最后一间房时，系统不会超卖。
8. 所有应付项目集中进入可视化账单中心，由用户调整、授权和付款。

### 2.2 可量化验收指标

- 搜索接口在测试数据规模下 P95 响应时间小于 800ms。
- 创建库存占用和确认订单接口 P95 响应时间小于 1s，不包含外部支付耗时。
- 并发预订测试中，可售库存永远不小于 0。
- 所有写接口支持幂等键，重复请求不会生成重复订单或重复扣款。
- 每次报价、库存变更、订单状态变更都有审计记录。
- API 文档、错误码、示例请求和 AI Tool Schema 与实际实现一致。
- 每笔应付费用都能关联到账单、业务来源和版本，不能产生无法在账单中心找到的“隐藏付款”。
- AI 无有效用户授权时，支付接口拒绝率必须为 100%。

## 3. 用户与权限

| 角色 | 主要能力 |
|---|---|
| 游客 | 搜索酒店、查看酒店和房型详情 |
| 用户 | 管理住客信息、创建预订、支付、查单、取消 |
| 酒店员工 | 维护被授权酒店的资料、房型、价格、库存和订单 |
| 酒店管理员 | 管理酒店员工、结算信息、酒店状态和操作权限 |
| 平台管理员 | 审核酒店、处理异常订单、封禁主体、查看全局审计 |
| AI Agent | 在用户授权范围内搜索、报价、创建占房、支付或取消 |

权限采用 RBAC，并在每个酒店维度进行数据隔离。酒店员工不能读取或修改其他酒店的数据。

## 4. MVP 功能范围

### 4.1 酒店端

- 酒店入驻、基本认证和审核状态。
- 酒店名称、简介、联系电话、完整地址、经纬度、时区、入住/退房时间。
- 酒店图片上传、封面设置、设施标签和服务说明。
- 房型管理：名称、床型、面积、最大入住人数、可加床、图片和设施。
- 价格计划：含早/不含早、可取消/不可取消、退改规则、最少连住天数。
- 日历库存：按日期维护总房量、停售状态、最少入住天数。
- 日历价格：按日期和价格计划维护价格，可按日期范围批量修改。
- 订单列表、订单详情、确认入住、标记离店和酒店侧取消。
- 数据概览：未来 7/30 天入住量、库存、订单金额和取消量。

### 4.2 用户端

- 目的地或当前位置搜索。
- 入住日期、离店日期、成人、儿童、房间数筛选。
- 酒店列表、地图位置、最低总价、可订状态。
- 酒店详情、房型、逐日价格、税费、退改政策和入住须知。
- 联系人和住客信息管理。
- 下单前二次报价。
- 统一的可视化账单中心，集中展示所有待支付、支付中、已支付、退款中和已关闭账单。
- 用户可以在账单列表中选择需要处理的账单，调整仍允许修改的预订内容，并在重新报价后付款。
- 账单支付、结果页、订单列表、订单详情和取消。
- 支付失败或网络中断后恢复订单状态。

### 4.3 AI 端

- 机器可读的 OpenAPI 3.1 文档。
- 面向 Agent 的精简 Tool Schema，避免 AI 直接拼接任意字段。
- 搜索、详情、报价、占房、确认、支付、查单和取消工具。
- 用户授权 Token、调用来源、会话 ID、幂等键和审计链路。
- 明确区分只读操作与产生费用/取消订单的高风险操作。
- 生产环境中，AI 在最终预订、付款和产生取消费前必须获得用户明确确认。
- AI 默认没有付款权限，只能读取经授权的账单摘要、整理待支付项并向用户发起付款授权请求。
- 用户可以在账单中心授予一次性、指定账单、指定金额上限和短时有效的付款授权；未获得有效授权时，AI 不能创建支付会话。

### 4.4 平台管理端

- 酒店审核、上下架和冻结。
- 用户、酒店员工和 AI 客户端管理。
- 订单检索和状态审计。
- 退款/取消异常处理。
- API Key、Webhook、限流规则和调用日志。

## 5. 暂不进入 MVP 的范围

- 酒店 PMS/渠道管理系统双向同步。
- 携程、Booking 等 OTA 渠道对接。
- 动态调价算法和收益管理。
- 会员积分、优惠券、评价社区、发票自动化。
- 多币种结算和复杂跨境税务。
- 酒店竞价排名。

这些能力应在核心库存和订单模型稳定后再做，否则会过早增加对账和并发复杂度。

## 6. 关键业务规则

### 6.1 日期与库存

- 预订使用“入住日包含、离店日不包含”的日期区间。
- 每个房型按酒店本地时区、按自然日维护库存。
- `可售库存 = 总库存 - 已确认库存 - 未过期占用库存`。
- 搜索结果只是当前快照，不能直接作为最终支付金额。
- 创建订单前必须重新报价并校验整个入住区间的库存。
- 占房默认保留 10 分钟，超时自动释放。
- 库存扣减必须在数据库事务中完成，并锁定对应日期的库存记录。

### 6.2 价格

- 金额统一使用最小货币单位整数保存，例如人民币分，禁止使用浮点数。
- 报价必须返回逐日房价、房间数、小计、税费、服务费、优惠和最终总价。
- 报价生成不可变快照，并设置 `expires_at`。
- 订单保存当时的价格、政策、税费和酒店关键资料快照；后续酒店改价不能影响已确认订单。

### 6.3 订单状态

建议状态机：

```text
DRAFT
  -> HOLDING
  -> PENDING_PAYMENT
  -> CONFIRMED
  -> CHECKED_IN
  -> COMPLETED

HOLDING / PENDING_PAYMENT -> EXPIRED
HOLDING / PENDING_PAYMENT / CONFIRMED -> CANCELLED
CONFIRMED / CANCELLED -> REFUND_PENDING -> REFUNDED
任意异常状态 -> MANUAL_REVIEW
```

状态只能通过规定动作转换，不能由前端直接提交任意目标状态。

### 6.4 取消

- 取消前先返回取消试算，包括是否可取消、退款金额、取消费和政策说明。
- 用户或 AI 再提交确认取消请求。
- 取消与退款分开记录；取消成功不等于退款已经到账。
- 酒店主动取消必须记录原因，并触发全额退款或人工处理。

## 7. AI 预订安全流程

### 7.1 AI 标准订房流程

AI 标准流程如下：

```text
理解用户需求
  -> 搜索可订酒店
  -> 获取候选酒店详情及政策
  -> 请求实时报价
  -> 向用户展示酒店、日期、房型、总价和退改政策
  -> 获得明确确认
  -> 创建限时占房
  -> 生成待支付账单并加入账单中心
  -> AI 发起付款授权请求，或把用户带到账单中心
  -> 用户在可视化账单中确认付款，或签发受限的一次性 AI 付款授权
  -> 服务端确认支付回调
  -> 查询并返回已确认订单
```

必须遵守以下约束：

- AI 不得自行编造 `hotel_id`、`room_type_id`、`quote_id` 或价格。
- AI 不得把搜索列表中的展示价当成最终总价。
- AI 必须展示最终总价、入住/离店日期、房型、取消政策和住客姓名后再请求用户确认。
- 订单创建、支付和取消都必须携带 `Idempotency-Key`。
- 高风险调用应携带 `user_confirmation_id`，由服务端验证其内容、有效期和对应报价。
- AI Token 采用细粒度 Scope，例如 `hotel:search`、`booking:create`、`booking:cancel` 和 `payment:authorization:request`。
- 普通 AI Token 不包含 `payment:execute`；即使用户在聊天中说“帮我付款”，也必须先生成平台可验证的付款授权。
- 默认不向第三方 Agent 返回完整身份证件号、支付凭据等敏感信息。
- 工具响应必须返回枚举状态和稳定错误码，不能只返回自然语言。

### 7.2 统一可视化账单中心

所有需要用户支付的项目都进入同一个账单中心，包括：

- 酒店订单房费、税费和服务费。
- 早餐、加床、接送等可选增值服务。
- 用户确认后产生的改期补差价。
- 按退改政策产生、并依法允许收取的取消费或其他应付费用。
- 后续扩展的其他旅行服务账单。

账单列表按“待确认、待支付、处理中、已支付、退款中、已退款、已关闭”分组，卡片至少展示：

- 账单来源、酒店/订单名称、账单号。
- 入住和离店日期、房型、住客或服务摘要。
- 原价、优惠、税费、附加费、已付金额和待付金额。
- 币种、付款截止时间、取消政策和账单状态。
- 是否允许调整、调整后是否需要重新报价。
- AI 是否正在申请付款授权，以及授权范围和到期时间。

用户可在账单中心执行：

1. 勾选一个或多个同币种、允许合并支付的账单。
2. 修改仍未锁定的入住日期、房型、房间数、增值服务或优惠选择。
3. 查看修改前后差额，并确认服务端生成的新报价。
4. 选择支付方式，在列表的支付抽屉或确认面板中完成付款。
5. 对暂不认可的账单选择“稍后处理”或“申请人工核对”。
6. 查看支付凭证、退款进度和完整状态时间线。

“用户可以调整”不表示可以直接编辑应付金额。房价、税费、取消费等服务端计算项保持只读；用户改变业务选项后，系统作废旧报价并重新生成账单版本，以保证酒店、支付和订单能够对账。

如果调整会影响库存，服务端必须在一个受控流程中重新校验库存、创建新报价和新占房，再释放旧占房；任一步失败都保留原有有效订单或给出明确恢复结果，不能出现账单已改但库存未改的中间状态。

账单状态建议为：

```text
DRAFT -> REQUIRES_REVIEW -> PENDING_PAYMENT -> PROCESSING -> PAID
                  ├─> EXPIRED
                  ├─> VOID
                  └─> DISPUTED -> MANUAL_REVIEW
PAID -> REFUND_PENDING -> PARTIALLY_REFUNDED / REFUNDED
```

### 7.3 AI 付款授权模型

默认模式下，AI 只能调用 `request_payment_authorization`，由手机端或 Web 账单中心弹出授权卡片。授权必须由已登录用户通过点击确认，并可结合支付密码、生物识别或支付机构验证完成。

一次付款授权至少包含：

| 字段 | 说明 |
|---|---|
| `authorization_id` | 不可猜测的一次性授权 ID |
| `user_id` | 授权人 |
| `agent_id` | 被授权的 AI Client/Agent |
| `bill_ids` | 只能支付的账单集合 |
| `max_amount` | 允许支付的最高金额，以最小货币单位保存 |
| `currency` | 唯一币种 |
| `expires_at` | 短时有效，建议 5 分钟 |
| `usage_limit` | 默认只能成功使用 1 次 |
| `quote_version` | 必须匹配用户看过并确认的账单版本 |
| `status` | `PENDING/GRANTED/USED/EXPIRED/REVOKED` |

授权规则：

- 没有 `GRANTED` 状态的有效授权，AI 调用支付接口必须返回 `PAYMENT_AUTHORIZATION_REQUIRED`。
- 账单金额增加、币种变化、账单集合变化或报价版本变化时，原授权立即失效。
- 实际支付金额可以低于授权上限，但不能高于上限。
- 用户可随时在付款前撤销授权。
- AI 不接触银行卡号、CVV、支付密码或生物识别信息。
- 授权、支付尝试和结果都写入不可篡改的审计记录。
- 推荐 MVP 采用“AI 整理并申请、用户最后点击付款”；只有确有需要时才开放一次性代理付款授权。

## 8. API 设计

### 8.1 设计原则

- API 前缀：`/api/v1`。
- JSON 字段使用 `snake_case`，时间使用带时区的 ISO 8601。
- 日期使用 `YYYY-MM-DD`，并明确以酒店本地时区解释。
- 所有列表接口使用游标分页。
- 所有写接口支持 `Idempotency-Key`。
- 每个响应返回 `request_id`，便于手机端、AI 和服务端共同排查。
- 使用一致错误结构：

```json
{
  "error": {
    "code": "INVENTORY_NOT_AVAILABLE",
    "message": "所选房型库存已变化",
    "retryable": true,
    "details": {
      "date": "2026-08-03"
    }
  },
  "request_id": "req_xxx"
}
```

### 8.2 用户与 AI 共用接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/v1/hotels/search` | 按位置、日期、人数和筛选条件搜索 |
| `GET` | `/api/v1/hotels/{hotel_id}` | 获取酒店详情 |
| `GET` | `/api/v1/hotels/{hotel_id}/offers` | 获取可订房型和价格计划 |
| `POST` | `/api/v1/quotes` | 生成实时、限时有效的价格快照 |
| `GET` | `/api/v1/quotes/{quote_id}` | 查询报价及是否过期 |
| `POST` | `/api/v1/bookings/holds` | 根据报价创建限时占房 |
| `POST` | `/api/v1/bookings` | 提交住客资料并创建待支付订单 |
| `GET` | `/api/v1/bookings/{booking_id}` | 查询订单真实状态 |
| `POST` | `/api/v1/bookings/{booking_id}/cancel-quote` | 计算取消结果 |
| `POST` | `/api/v1/bookings/{booking_id}/cancel` | 确认取消 |

`POST /bookings` 不能信任客户端上传的金额，只能使用服务端有效的 `quote_id` 计算和落库。

### 8.3 账单与付款授权接口

| 方法 | 路径 | 作用 | 权限 |
|---|---|---|---|
| `GET` | `/api/v1/bills` | 获取统一账单列表和聚合金额 | 用户；AI 需 `bill:read` |
| `GET` | `/api/v1/bills/{bill_id}` | 获取账单明细、版本和时间线 | 用户；AI 需 `bill:read` |
| `POST` | `/api/v1/bills/{bill_id}/adjustments` | 修改允许调整的业务选项并重新报价 | 用户；AI 只能提交建议 |
| `POST` | `/api/v1/payment-batches/preview` | 预览多个账单的合并支付结果 | 用户 |
| `POST` | `/api/v1/payment-authorizations/requests` | AI 请求用户授权指定账单付款 | AI 可调用 |
| `POST` | `/api/v1/payment-authorizations/{id}/grant` | 用户授予一次性付款权限 | 仅用户交互 |
| `POST` | `/api/v1/payment-authorizations/{id}/revoke` | 用户撤销授权 | 仅用户 |
| `POST` | `/api/v1/payment-sessions` | 创建实际支付会话 | 用户，或携带有效受限授权的 AI |
| `GET` | `/api/v1/payment-sessions/{id}` | 查询支付真实状态 | 用户；受限 AI |

账单查询允许 AI 帮用户归类和解释，但默认隐藏完整住客隐私数据。`grant` 接口必须拒绝纯 AI Token，不能让 Agent 自己批准自己的授权请求。

### 8.4 酒店管理接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/v1/merchant/hotels` | 创建酒店 |
| `PATCH` | `/api/v1/merchant/hotels/{hotel_id}` | 修改酒店资料 |
| `POST` | `/api/v1/merchant/hotels/{hotel_id}/media` | 上传图片 |
| `POST` | `/api/v1/merchant/hotels/{hotel_id}/room-types` | 创建房型 |
| `POST` | `/api/v1/merchant/hotels/{hotel_id}/rate-plans` | 创建价格计划 |
| `PUT` | `/api/v1/merchant/inventory/bulk` | 批量设置日期库存 |
| `PUT` | `/api/v1/merchant/rates/bulk` | 批量设置日期价格 |
| `GET` | `/api/v1/merchant/bookings` | 酒店订单列表 |
| `POST` | `/api/v1/merchant/bookings/{booking_id}/check-in` | 确认入住 |

批量价格和库存接口需要限制日期跨度、校验酒店归属，并完整记录操作前后值。

### 8.5 Webhook

- `bill.created`
- `bill.updated`
- `payment.authorization_requested`
- `payment.authorization_granted`
- `payment.authorization_revoked`
- `booking.confirmed`
- `booking.cancelled`
- `booking.expired`
- `payment.succeeded`
- `payment.failed`
- `refund.succeeded`
- `inventory.low`

Webhook 使用签名、时间戳和事件 ID；接收方可以安全地重复消费同一个事件。

### 8.6 面向 AI 的 Tool 集合

首版只暴露 10 个高层工具：

1. `search_hotels`
2. `get_hotel_details`
3. `create_quote`
4. `create_booking_hold`
5. `create_booking`
6. `list_bills`
7. `get_bill_details`
8. `request_payment_authorization`
9. `get_booking`
10. `preview_and_cancel_booking`

Tool 返回内容应短而完整，使用 ID、枚举、金额和下一步动作。普通订房 Agent 不暴露无授权的 `execute_payment`，酒店后台的低层库存编辑接口也不直接暴露。

当平台允许代理付款时，可以在用户授予有效的一次性授权后，临时向对应 Agent 开放 `execute_authorized_payment`。该工具只能消费授权绑定的账单版本，执行成功、失败或授权过期后立即失效，不能成为 AI 的长期权限。

## 9. 核心数据模型

### 9.1 主要实体

| 实体 | 关键字段 |
|---|---|
| `users` | 身份、联系方式、状态 |
| `organizations` | 酒店集团或单体酒店经营主体 |
| `organization_members` | 组织成员和角色 |
| `hotels` | 名称、地址、经纬度、时区、审核/上下架状态 |
| `hotel_media` | 图片对象地址、类型、排序 |
| `amenities` | 标准设施字典 |
| `room_types` | 酒店、容量、床型、面积、状态 |
| `rate_plans` | 餐食、退改政策、入住限制 |
| `daily_inventory` | 房型、日期、总量、已售、占用、停售 |
| `daily_rates` | 价格计划、日期、币种、基础价格 |
| `quotes` | 查询条件、逐日明细、政策快照、总价、过期时间 |
| `inventory_holds` | 报价、日期范围、房量、过期时间、状态 |
| `bookings` | 订单号、用户、酒店、状态、金额和快照 |
| `booking_guests` | 入住人信息 |
| `bills` | 账单来源、订单、用户、币种、状态、版本、到期时间 |
| `bill_items` | 房费、税费、服务费、优惠和附加项明细 |
| `bill_adjustments` | 用户调整内容、调整前后版本和重新报价结果 |
| `payment_batches` | 用户勾选的一组待支付账单和聚合金额 |
| `payment_authorizations` | 指定 AI、账单、金额上限、版本、有效期和使用次数 |
| `payments` | 支付单、渠道、状态、金额 |
| `refunds` | 退款单、状态、金额 |
| `idempotency_keys` | 调用主体、接口、请求摘要、响应 |
| `audit_logs` | 操作者、动作、对象、前后值、来源 |
| `outbox_events` | 待可靠投递的领域事件 |

### 9.2 数据约束

- `daily_inventory(room_type_id, stay_date)` 唯一。
- `daily_rates(rate_plan_id, stay_date)` 唯一。
- 对外订单号唯一，数据库内部 ID 不直接体现业务规律。
- 所有记录带 `created_at`、`updated_at`，关键业务记录支持软删除或禁止删除。
- 酒店、房型和价格计划一旦被订单引用，不允许物理删除。
- 报价和订单快照使用 JSONB 保存，但可查询核心字段仍应单独建列。
- 已进入支付流程的账单版本不可覆盖更新；调整业务内容必须生成新版本并保留旧版本。
- 付款授权必须绑定账单版本，不能跨用户、跨币种或跨版本复用。

## 11. 与现有手机软件的集成

现有 `Qwen_competition` 手机端是 React 界面通过 Tauri Android 打包、后端运行在电脑或服务器上的远程客户端模式。酒店能力应按同样方式集成：

1. `hotel_book` 独立运行后端和数据库。
2. 现有 React Console 增加“酒店”入口及移动端底部导航。
3. 手机端配置 `HOTEL_BOOKING_API_BASE_URL`，公网环境只使用 HTTPS。
4. 登录后由统一身份服务签发可访问酒店 API 的 Token；MVP 过渡期也可通过服务端 Token Exchange，不能把管理员 API Key 写进 APK。
5. 手机端复用 OpenAPI 生成的 TypeScript Client。
6. AI 主 Agent 通过酒店 Tool/Skill 调用同一 API，并把结构化订单结果呈现在手机端对话和订单页。
7. 手机端增加“账单”入口和全局待支付数量徽标；账单列表、调整、授权和支付在统一界面完成。
8. 支付由账单中心请求后端创建一次性支付会话；AI 默认只能把授权请求推送到该界面，支付结果以服务端回调为准。

建议的用户入口：

- 对话中说“帮我订明晚澳门附近的酒店”，AI 返回候选卡片。
- 用户点击卡片进入酒店详情或继续让 AI 筛选。
- 最终确认页必须是结构化页面，明确展示总价和取消政策。
- AI 产生待支付订单后，账单自动进入账单中心；用户可以调整、授权或直接付款。
- 订房成功后同时进入“我的订单”，不能只保留在聊天记录中。

## 12. 安全、隐私与合规

- 密码使用安全哈希；Token 短时有效并支持刷新、撤销和设备管理。
- 酒店后台、平台后台、AI Client 使用不同授权范围。
- API 全量启用 HTTPS，敏感配置只存在服务端密钥管理中。
- 不存储银行卡号和 CVV，交给合规支付机构托管。
- 身份证件、手机号等敏感字段加密并限制日志输出。
- 图片上传检查 MIME、文件大小和恶意内容，使用随机对象名。
- 对登录、搜索、报价、下单、取消和图片上传分别限流。
- 酒店资料、库存、价格、订单和退款操作进入不可随意修改的审计日志。
- AI 付款授权采用一次性随机凭据，仅保存哈希或不可逆摘要，并绑定用户、Agent、账单版本、币种、金额上限和有效期。
- 明确隐私政策、用户协议、酒店协议、取消与退款说明。
- 上线真实交易前，根据运营地区完成经营资质、支付、隐私和消费者保护合规审查。

## 13. 测试策略

### 13.1 必测场景

- 跨月、跨年、闰日、夏令时和酒店不同时区。
- 最后一间房被两个请求同时预订。
- 同一个幂等键重复创建订单或支付。
- 报价过期、占房过期、支付回调延迟和重复回调。
- 支付成功但客户端断网。
- 取消成功但退款失败。
- 酒店改价后，已有报价和已确认订单金额不变。
- 一名用户订多间房、多位住客、儿童入住限制。
- 酒店员工越权访问另一家酒店。
- AI 缺少用户确认时尝试下单或取消。
- AI 未获得付款授权时尝试创建支付会话。
- AI 使用已过期、已撤销、已使用或账单版本不匹配的付款授权。
- 用户调整日期、房型或服务后，旧账单和旧付款授权失效。
- 多账单合并支付中存在不同币种、过期账单或已支付账单。
- 用户支付期间切换后台、断网或重复点击付款。

### 13.2 测试层级

- 单元测试：价格计算、日期区间、政策和状态机。
- 数据库集成测试：事务、行锁、库存扣减和事件 Outbox。
- API 合同测试：OpenAPI 与实际请求/响应一致。
- E2E：酒店发布库存—用户搜索—预订—支付—取消完整链路。
- 并发测试：最后库存、重复请求、回调风暴。
- 手机端测试：弱网、切后台、Token 过期、支付返回。
- AI 评测：缺失信息追问、候选比较、确认门禁、错误恢复。

## 14. 分阶段实施

### 阶段 0：合同与原型（第 1 周）

- 确定用户身份、酒店审核、支付方式、地图服务和首发地区。
- 固化数据模型、订单状态机、库存算法和错误码。
- 产出 OpenAPI 初稿和关键页面线框。
- 准备 10 家酒店、30 个房型、90 天价格库存的种子数据。

验收：产品、前端、后端和 AI 都能基于同一份接口合同工作。

### 阶段 1：核心后端（第 2～3 周）

- 完成认证、酒店、房型、价格计划、每日价格和库存。
- 完成搜索、详情、报价和库存占用。
- 完成订单、账单状态机、幂等、审计和过期释放任务。
- 完成账单版本、支付批次和一次性付款授权服务。
- 建立数据库迁移和自动化测试。

验收：纯 API 可以从发布库存走到创建待支付订单及账单，并通过并发库存和未授权付款拒绝测试。

### 阶段 2：酒店后台（第 3～4 周）

- 完成酒店资料、图片、房型和价格计划页面。
- 完成价格库存日历和批量编辑。
- 完成订单列表和入住操作。

验收：酒店员工无需直接操作数据库即可维护未来 90 天房量和价格。

### 阶段 3：用户前端与手机端（第 4～5 周）

- 完成搜索、列表、地图、详情、报价确认、订单页和统一账单中心。
- 完成账单分组、调整后重新报价、合并支付预览、支付抽屉和状态时间线。
- 接入现有 React/Tauri 手机 App。
- 完成登录、Token 刷新、弱网和支付返回状态恢复。

验收：Android 客户端可在统一账单列表中查看、调整并支付测试订单，网络中断后能够恢复真实支付状态。

### 阶段 4：AI 接入（第 5～6 周）

- 发布 OpenAPI 和 Agent Tool Schema。
- 实现 AI Scope、确认门禁、调用审计和稳定错误恢复。
- 实现 AI 付款授权请求、用户授权卡片、一次性授权校验和撤销。
- 在现有主 Agent 中增加酒店预订 Skill/Tool。
- 建立 AI 场景评测集。

验收：AI 可以根据自然语言完成候选搜索和比较；只有在明确确认后才能创建占房和订单；没有用户付款授权时无法创建支付会话。

### 阶段 5：支付、运营与上线（第 6～7 周）

- 接入支付沙箱、Webhook、取消和退款。
- 增加监控、告警、备份、恢复演练和管理后台。
- 完成安全检查、性能测试和小流量发布。

验收：支付结果可恢复、订单可对账、关键异常有告警和人工处理入口。

## 15. 上线门槛

上线前必须同时满足：

- 库存并发和幂等测试通过。
- 支付、取消、退款、回调重放和对账演练通过。
- 数据库自动备份及恢复演练通过。
- 手机端在真实 Android 设备和弱网环境验证通过。
- AI 未确认下单、价格变化、库存变化、Token 过期等评测通过。
- 统一账单中心、重新报价、付款授权撤销和授权越权测试通过。
- 普通 AI Token 无法直接付款，付款授权只能由用户界面授予。
- API Key、支付密钥、数据库密码均未进入代码库或 APK。
- 有客服/运营处理异常订单和退款的流程。
- 有隐私政策、用户协议和取消政策。

## 16. 关键指标与监控

### 业务指标

- 搜索到详情转化率。
- 详情到报价转化率。
- 报价到占房、占房到支付、支付到确认转化率。
- 取消率、退款成功率、超时占房率。
- 酒店库存覆盖天数和低库存房型数。
- AI 预订成功率、人工接管率、用户确认放弃率。
- 待支付账单数量、账单调整率、付款授权请求通过率和授权后支付成功率。

### 技术指标

- API P50/P95/P99 延迟和错误率。
- 数据库锁等待、库存冲突和死锁。
- 支付回调延迟、重复回调和对账差异。
- 异步任务堆积、Webhook 失败和重试次数。
- AI 工具错误码分布和未授权高风险调用次数。
- 过期、撤销、超额、跨账单版本等 AI 付款授权拒绝次数。

## 17. 开工前必须确认的产品决策

以下决策不会阻止骨架开发，但必须在接入真实支付前明确：

1. 首发地区是澳门、内地还是其他地区；这会影响地图、币种、支付和合规。
2. 平台是否代收房费，还是只生成订单后到店付款。
3. 酒店入驻由平台审核，还是演示环境允许自动通过。
4. 用户登录使用手机号、邮箱还是复用现有 QwenPaw 身份。
5. 酒店是使用独立 Web 后台，还是也需要独立酒店员工 App。
6. AI 是否允许在用户签发一次性、限额、指定账单的授权后代理支付；建议 MVP 先由 AI 发起授权请求、用户在账单中心最终点击付款。
7. 首版是否只支持一种币种；建议按酒店固定币种，MVP 不做换汇。

## 18. 推荐的第一批开发任务

1. 初始化后端、PostgreSQL、迁移和测试框架。
2. 实现 `hotels`、`room_types`、`rate_plans`、`daily_inventory`、`daily_rates`。
3. 编写日期库存查询和原子占房服务。
4. 固化报价 JSON 和订单状态机。
5. 设计统一账单、账单版本、支付批次和付款授权模型。
6. 先完成 OpenAPI 合同，再生成前端客户端。
7. 用种子数据跑通“搜索—报价—占房—订单—账单”API。
8. 完成并发最后一间房、重复幂等请求和 AI 无授权付款测试。
9. 再开始酒店管理日历、用户搜索页面和可视化账单中心。

优先级原则：先保证交易正确，再做页面丰富度；先让 API 对人类前端和 AI 同时稳定可用，再增加更多渠道。
