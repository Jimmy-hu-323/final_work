# 人流密度数据发布器 — 项目说明

文档版本：2026-07-26　　当前程序版本：v1.1.0
项目目录：`G:\travel_app\data_publish\data_publish`
适用对象：项目维护者、后续开发模型、要接入这份数据的前端开发者

> 想快速跑起来看 `README.md`；想知道每个版本改了什么看 `versions/`；
> 本文说明的是**为什么这样设计**，以及怎么接进主项目。

---

## 1. 这是什么

一个独立的小型 Web 服务，用来**人工发布各城市区 / 街道 / 景点的人流密度数据**。

它是 LensGo × QwenPaw 澳门旅行智能眼镜项目的配套工具，不是那个项目的一部分：

```text
┌─────────────────────────┐        ┌──────────────────────────────┐
│  人流密度数据发布器      │  HTTP  │  LensGo × QwenPaw 主项目      │
│  （本项目，独立进程）     │ ─────▶ │  人流密度地图页（待实现）      │
│  你在这里手动发布数据     │  JSON  │  用户在这里看颜色深浅          │
└─────────────────────────┘        └──────────────────────────────┘
```

主项目那边要做的是「用颜色展示每个区域有多少人、放大逐级细化」的地图页；
真实客流数据拿不到，所以由本工具充当数据源。

**本项目不修改主项目的任何文件**，两边只通过 HTTP 通信。

## 2. 为什么不直接用文件投递

最省事的做法是「发布器写一个 JSON，主项目轮询这个文件」。没有这么做，原因有三：

1. 主项目文档在讲 Console 媒体同步时明确写过「不能依赖目录轮询」，这是它们
   踩过坑后定下的规矩。
2. 文件方案会出现「写到一半被读到」的半截数据。
3. 跨机器就不能用了。

所以做成了**服务 + API**：写和读走同一个进程、同一个 SQLite，天然单一事实来源。

## 3. 技术选型

| 选择 | 理由 |
|---|---|
| Python 标准库（`http.server` + `sqlite3`） | 目标机器没装 FastAPI。发布器应该 `python run.py` 就能跑，不该为一个内部工具引入依赖安装步骤 |
| SQLite 单文件 | 单人使用、需要事务和历史查询，够用且零运维 |
| 原生 JS + Leaflet，无构建 | 改一行 HTML 刷新即可，不需要 npm/vite。Leaflet 版本与主项目一致（1.9.4） |
| Leaflet 本地化到 `web/vendor/` | 本地工具不该因为断网或 CDN 不可达就整页打不开 |

代价是没有 FastAPI 的自动 `/docs`，所以接口文档写在页面的「API 说明」标签页
和本文里。业务逻辑全部集中在 `store.py`，将来要换框架或并进主项目，只需重写
`api.py` 这一薄层。

## 4. 模块职责

```text
run.py            启动入口：参数解析、建库、按需灌种子数据、起服务
app/config.py     运行配置、.env 读取、拥挤度分级阈值
app/geo.py        WGS-84 → GCJ-02 坐标转换
app/amap.py       高德 Web 服务客户端（POI 搜索 / 周边 / 逆地理编码）
app/db.py         表结构 + 增量迁移（ALTER TABLE ADD COLUMN）
app/store.py      全部 SQL 与业务校验 ← 核心，换框架时唯一要保留的
app/auth.py       读写令牌与本机白名单
app/api.py        路由表、鉴权分发、静态文件、错误码映射
app/seed_data.py  内置城市 / 区 / 街道 / 景点
web/              发布页面（5 个标签页）
```

分层原则：`api.py` 只做「解析请求 → 调 store → 序列化响应」，不含业务判断；
所有校验、去重、坐标转换都在 `store.py`。

## 5. 数据模型

### 5.1 四张表

```text
cities    城市：id、名称、中心点、默认缩放、adcode
regions   区域：id、city_id、parent_id、level、名称、别名、中心点、
                半径、面积、geometry、高德来源信息
batches   批次：id、发布者、备注、状态、条数、时间
readings  读数：region_id、batch_id、观测时间、人数、拥挤度、备注
```

### 5.2 三级层级

`regions.level` 只有三个取值，与地图的三档缩放一一对应：

| level | 含义 | 地图缩放 | 例子 |
|---|---|---|---|
| `district` | 区 / 堂区 | 远 | 大堂区、路氹填海区 |
| `street` | 街道 | 中 | 新马路、官也街 |
| `poi` | 景点 | 近 | 大三巴牌坊、威尼斯人 |

`parent_id` 串起层级（景点 → 街道 → 区）。没有著名景点的地方，最细就到街道
——这与需求一致，不强求每条街都挂景点。

### 5.3 坐标系：库里只存 GCJ-02

这是整个项目最容易出错、也最重要的一条约定。

主项目 `TravelPlanner` 用的是高德栅格瓦片，属于 GCJ-02；它存的坐标也是
GCJ-02 的 `"lng,lat"`。而 GPS、维基、OpenStreetMap 给的是 WGS-84。两者
在澳门一带相差 **300~600 米**，直接混用会让整张图错位半个氹仔。

处理规则：

- **入库前统一转成 GCJ-02**，由 `geo.to_gcj02()` 按声明的 `coord_system` 转换。
- 内置种子数据用 WGS-84 书写（公开资料就是这个坐标系），灌库时转换。
- 高德接口返回的坐标**本来就是 GCJ-02**，这条路径不做任何转换。
- API 返回的每个区域都带 `"coord_system": "gcj02"`，前端不需要再转。

实测：大三巴牌坊 WGS-84 `[113.5406, 22.1976]` → GCJ-02
`[113.5457, 22.1947]`，偏移约 500 米，与预期一致。

### 5.4 拥挤度分级

两个字段各司其职：

- `people_count`：原始人数，给用户看具体数字；
- `crowd_level`：0~4 的分级，**决定地图颜色**。

区和景点的人数量级差很多（景点 800 人是挤爆，一个区 800 人是空荡），所以
阈值按层级分开定义（`config.CROWD_THRESHOLDS`）：

| level | 0 空旷 | 1 较少 | 2 适中 | 3 拥挤 | 4 非常拥挤 |
|---|---|---|---|---|---|
| district | <1000 | 1000 | 5000 | 15000 | 30000+ |
| street | <100 | 100 | 500 | 1500 | 3000+ |
| poi | <50 | 50 | 200 | 500 | 1000+ |

发布时不填 `crowd_level` 就自动推导，也可以手动覆盖。这是启发式阈值，不是
行业标准，可以随时改。

### 5.5 「无数据」不是「0 人」

`/api/density/latest` 里 `reading` 为 `null` 表示这个区域**从来没有发布过数据**，
和「发布了 0 人」是两回事。前端必须用不同视觉表现（灰色斜纹 vs 色阶最浅端），
否则会让人以为那里真的没人。这是热力图最常见的误导来源。

### 5.6 批次

一次发布 = 一个 `batch_id`，整批写入或整批失败，不会出现半截数据被地图读到。
撤销时删掉该批读数、批次记录保留 `reverted` 状态留痕。

`readings` 保留全部历史而不是只存最新，成本几乎为零，但以后想做时间轴回放或
趋势曲线就是白送的。

## 6. 两条发布路径

### 6.1 地图发布（主要方式）

```text
搜索地点 ──▶ 高德 POI 搜索 ──▶ 点结果 ──▶ 地图飞过去 ──┐
                                                      ├─▶ 填人数 ─▶ 发布
点击地图 ──▶ 逆地理编码 ──▶ 带出地址 + 附近 POI ──────┘
                                                        │
                                          自动登记 region + 写入一条读数
```

发布时会先调 `POST /api/regions/from-amap` 把地点登记进库，再调
`POST /api/readings` 写读数。两步都成功才算发布完成。

去重规则：

- 有高德 POI id 的，按 `(external_source='amap', external_id)` 唯一索引去重，
  同一个地点重复添加返回已有记录；
- 纯坐标点击的，按「同城 + 同名 + 30 米内」判定为同一个地点。

城市归属（这决定了"高德能搜到的任何地址都能加"是否成立）：

1. 高德城市名命中内置别名（澳门特别行政区 → `macau`）→ 用内置城市；
2. adcode 已经建过 → 复用；
3. 名称完全一致 → 复用；
4. 都不匹配 → 按 adcode 自动新建 `amap-<adcode>` 城市；
5. 高德没给城市名（例如没配 Key 时直接点地图）→ 就近归属到 80 公里内最近的
   已有城市；超出范围才报错要求指定。

### 6.2 批量发布

从本库已有区域里搜索、多选、一次填多个人数、一次性发布。适合演示前批量造数据，
配合「随机填充」按层级生成量级合理的随机人数。

## 7. 高德接入的边界

**Key 只存在服务端，浏览器永远拿不到。**

```text
浏览器 ──▶ 本服务 /api/amap/search ──▶ 高德 restapi.amap.com
           （带 Key，服务端加上）
```

这与主项目 `travel_planner.py` 的做法一致（"高德 Key 只在服务端环境或 .env
中读取，不发送到浏览器"）。如果把 Key 放前端，任何人打开页面源码就能拿走。

Key 从 `data_publish/.env` 读取（`config.load_env_file()`），该文件已被
`.gitignore` 忽略。**必须是「Web服务」类型的 Key**，用「Web端(JS API)」类型
会返回 `USERKEY_PLAT_NOMATCH`（10009）——主项目 `START_LOCAL.md` 里踩过同样的坑。
`amap.INFOCODE_HINTS` 把常见错误码翻译成了可读中文。

没有 Key 时：地图底图、已有数据展示、批量发布、撤销全部正常，只有「搜索地点」
和「点击反查地址」不可用，页面顶部有明确提示，接口返回 502 + 可读原因。

## 8. API

读接口默认公开（地图前端要直接调）；写接口在未设 `CROWD_WRITE_TOKEN` 时
**只接受本机请求**。

| 方法 | 路径 | 说明 | 写 |
|---|---|---|:-:|
| GET | `/api/health` | 服务状态、版本、数据量统计 | |
| GET | `/api/meta` | 层级、分级标签、推导阈值、当前权限 | |
| GET | `/api/cities?q=` | 搜索城市 | |
| GET | `/api/regions?city_id=&level=&parent_id=&q=&limit=&offset=` | 搜索区域 | |
| GET | `/api/regions/{id}` | 区域详情 | |
| GET | `/api/regions/{id}/history` | 该区域历史读数 | |
| GET | `/api/density/latest?city_id=&level=&include_empty=` | **地图页主接口** | |
| GET | `/api/amap/status` | 高德 Key 是否已配置 | |
| GET | `/api/amap/search?q=&city=` | 高德 POI 搜索 | |
| GET | `/api/amap/around?lng=&lat=&radius=` | 高德周边搜索 | |
| GET | `/api/amap/regeo?lng=&lat=` | 逆地理编码 | |
| GET | `/api/batches` / `/api/batches/{id}` | 发布历史 / 批次明细 | |
| POST | `/api/readings` | 发布一批数据 | ✓ |
| POST | `/api/regions/from-amap` | 登记高德地点（幂等） | ✓ |
| POST | `/api/cities` / `/api/regions` | 新增城市 / 区域 | ✓ |
| DELETE | `/api/batches/{id}` | 撤销批次 | ✓ |

错误码约定：

| 状态码 | 含义 |
|---|---|
| 400 | 请求数据不合法（`ValidationError`） |
| 401 / 403 | 令牌无效 / 非本机写入被拒（`AuthError`） |
| 404 | 目标不存在（`NotFoundError`） |
| 502 | 高德侧问题或未配置 Key（`AmapError`）——不是本服务的错 |
| 500 | 本服务内部错误，详见服务端日志 |

## 9. 安全边界

当前定位是**本机 / 受控内网的内部工具**，不适合直接裸露到公网。

已经做到的：

- 写接口默认只允许回环地址；设了 `CROWD_WRITE_TOKEN` 后按 Bearer 校验。
- 高德 Key、令牌只在 `.env`，已被 `.gitignore` 排除。
- 静态文件服务做了路径穿越防护（`/../run.py` 返回 403）。
- 所有用户可控文本在前端渲染前做 HTML 转义。
- 请求体大小上限 4 MB，单次发布上限 500 条。
- 出错时主动断开连接，避免未读完的请求体污染 HTTP/1.1 keep-alive 的下一个请求。

要对外开放还需要补的：

- HTTPS（当前是明文 HTTP）；
- 读接口也上令牌，或放在反向代理后；
- 请求限流（高德接口有日调用量，代理层应加限流避免被刷爆额度）。

## 10. 怎么接进主项目

地图页要的数据一个接口就够：

```bash
curl "http://127.0.0.1:18099/api/density/latest?city_id=macau&level=poi&include_empty=0"
```

返回结构（节选）：

```json
{
  "generated_at": "2026-07-26T12:00:00Z",
  "count": 24,
  "items": [
    {
      "region_id": "macau-poi-ruins-st-paul",
      "name": "大三巴牌坊",
      "level": "poi",
      "parent_id": "macau-s-sao-paulo",
      "center": [113.5457, 22.1947],
      "coord_system": "gcj02",
      "radius_m": 120,
      "geometry": null,
      "reading": {
        "people_count": 860,
        "crowd_level": 3,
        "observed_at": "2026-07-26T11:58:00Z",
        "batch_id": "batch_9ae953c3aa39"
      }
    }
  ]
}
```

前端要注意的三点：

1. `reading: null` 是「无数据」，不能当 0 人渲染；
2. `observed_at` 是 UTC，应显示相对时间，超过 30 分钟标记为「已过期」；
3. `geometry` 目前恒为 `null`，先用 `center` + `radius_m` 落点。等多边形补上后
   同一接口会直接返回 GeoJSON，**前端结构不用改**。

关于地图页的后端落在哪，之前分析过三个方案（QwenPaw router / 挂 LensGo :18866 /
外层新服务）。现在多了第四个、也可能是最省事的选项：**主项目地图页直接消费本
服务的接口**，不再单独建后端。代价是主项目多依赖一个进程，好处是这份数据只有
一个来源、一套代码。这个选择还没定。

## 11. 当前边界与待决策

刻意留到后续版本的，不是遗漏：

| 项 | 现状 | 需要先定什么 |
|---|---|---|
| 区域多边形 | `geometry` 恒为 null，只有中心点+半径 | 街道级用手绘近似多边形还是网格热力图 |
| 层级聚合 | 区的人数必须单独发布，不由街道求和 | 采用「有独立值用独立值、没有就求和」的混合规则？表结构已支持，加聚合不用改库 |
| 高德接口实测 | 只验证了无 Key 时的降级 | 需要一个「Web服务」类型的 Key |
| 发布页地图点选区域 | 只能点坐标，不能点区域面 | 依赖多边形数据 |
| 并发 | 单机 SQLite，单人使用 | 多人同时发布时再考虑换库 |

## 12. 诚信提示

这些是**人工发布的模拟数据**，不是官方实时客流。接进主项目展示时，界面上应
保留数据来源和更新时间的标注，避免看的人误以为是真实监测数据。主项目文档
反复强调「外部服务缺失时显示降级状态，不伪造数据」，这条同样适用。

内置种子数据的坐标是人工整理的近似值，精度够做分区着色，但不是测绘数据。
需要修正直接改 `app/seed_data.py`，然后 `python run.py --reseed`。

## 13. 版本记录

每个版本改了什么、实现了什么，记录在 `versions/` 目录：
